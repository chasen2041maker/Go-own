# 原创性与素材边界声明

## 1. 声明目的

“投资内容社区与治理系统”是为学习 Go 后端工程而独立设计的个人作品。它使用内容社区中常见的公开概念——账户、圈子、帖子、评论、举报、治理与审计——重新推导领域规则、接口契约、数据约束和测试场景，不以任何商业系统作为实现蓝本。

本文既是作品说明，也是后续贡献的硬边界。任何实现、示例或文档若不能满足这里的要求，都不应进入仓库。

## 2. 原创范围

下列内容均从本项目的学习目标和业务故事独立设计：

- 模块化单体的分层方式与依赖方向；
- HTTP 资源、请求响应、稳定错误码和权限矩阵；
- MySQL 表、字段、外键、唯一约束、索引与迁移顺序；
- 举报处理、隐藏、恢复和审计的状态机；
- 领域测试、用例测试、Handler 测试、MySQL 集成测试与黑盒验收场景；
- `reference` / `starter` 双轨学习结构以及八阶段教学顺序；
- 演示用账户、圈子、股票代码、内容和操作记录。

相同的通用术语不代表实现相同。例如“帖子”“评论”“举报”是行业通用概念，本项目仍要求围绕自己的不变量重新命名、建模和测试。

## 3. 明确禁止带入的材料

任何贡献都不得包含或改写以下材料：

- 任职单位、客户或其他非公开项目的源码、伪代码、目录结构和内部命名；
- 非公开接口契约、数据库表结构、迁移文件、测试用例或运维脚本；
- 真实用户资料、内容、行为日志、交易信息或生产数据样本；
- 密钥、令牌、连接串、内部域名、环境变量值或基础设施标识；
- 商标、Logo、截图、配色、文案、角色形象等品牌资产；
- 通过逐字替换标识符掩盖来源的“改名式复制”。

发现来源不明的片段时，默认不使用。应先回到本项目规格，用业务约束重新推导最小实现。

## 4. 可使用的公开知识

允许依据以下公开知识进行独立实现：

- Go、MySQL、HTTP、JWT、密码哈希、OpenAPI、Docker 和 GitHub Actions 的官方文档；
- RFC、SQL 事务与索引等公开标准或通用计算机科学知识；
- 开源依赖公开文档中描述的 API 使用方式，但必须遵守其许可证；
- 内容社区普遍存在的产品概念，但不得照搬某个产品的专有流程、文案或视觉资产。

引用外部资料时只记录必要出处和所学原理，不把大段外部实现复制到项目中。

## 5. 虚构数据与投资风险

Seed 中的证券代码、证券名称、交易所、用户、圈子和帖子内容必须完全虚构。数据只用于演示多对多关系、过滤、分页、权限和治理，不连接真实行情，也不构成投资建议。

测试不得依赖真实证券代码“碰巧存在”。一条证券记录是否可用于新帖子，只由本项目数据库中的 `status=active` 决定。

## 6. 双轨隔离

`reference/` 是完整参考实现，`starter/` 是学习者亲手实现的空间。二者可以共同遵守 `contracts/` 中的 OpenAPI 和黑盒行为，但不得互相导入业务代码、复制内部包或通过软链接共享实现。

这条边界有两个目的：

1. 证明验收来自对外行为，而不是对某个内部写法的耦合；
2. 让学习者可以采用不同实现，只要不破坏契约和领域不变量。

## 7. 中文注释原则

中文注释解释“为什么”，重点放在：

- 权限为何必须取自已验证身份，而不能信任请求体；
- 某组写操作为何必须处于同一事务；
- 唯一键、外键或行锁保护了什么并发不变量；
- 删除与治理隐藏为何使用两个独立状态；
- 错误为何被映射为某个稳定业务码；
- 看似多余的排序字段为何保证分页稳定。

不要逐行翻译 Go 语法，不写“给变量赋值”“进入循环”之类注释，也不要用注释弥补含糊命名。若规则可以由测试清楚表达，注释应补充测试难以说明的设计动机，而不是重复断言。

## 8. 提交前原创性检查

每次合并前至少确认：

- [ ] 所有文件都能说明其业务需求来源；
- [ ] 未出现任职单位、客户、内部系统或真实品牌标识；
- [ ] 示例数据为虚构数据，且不含个人信息；
- [ ] 接口、表结构和测试由当前规格推导，而非对其他系统做字段映射；
- [ ] 新依赖来自公开渠道，许可证和用途清楚；
- [ ] 日志、夹具和文档没有密码、Token、连接串或内部地址；
- [ ] 中文注释解释原因、不变量和取舍，不逐行翻译代码；
- [ ] `starter` 没有导入或复制 `reference` 的业务实现。

如任何一项无法确认，应暂停提交，删除可疑材料，再从公开需求重新实现。
